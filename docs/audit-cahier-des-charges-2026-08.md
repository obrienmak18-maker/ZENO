# Audit de conformité CLASSE — cahier des charges contre dépôt réel

## Conclusion exécutive

Le dépôt ZENO contient une **fondation technique compilable**, mais il ne satisfait pas encore le niveau « plateforme scolaire réellement exploitable en production » demandé par le cahier des charges. Les principaux écarts sont fonctionnels, pas seulement cosmétiques : plusieurs écrans desktop restent alimentés par des données initiales/localStorage, le mobile comporte des parcours codés en dur, `packages/ui` n’est pas un design system de composants, et plusieurs domaines n’ont pas encore d’API Firebase.

La publication sur `main` ne doit donc pas être interprétée comme une conformité complète au cahier. Elle correspond à une migration monorepo et à un socle Firebase/Emulator, pas à la clôture de tous les modules métiers.

## Matrice de conformité

| Domaine du cahier | Exigence | État réel | Preuve / écart |
|---|---|---|---|
| Stack backend | Firestore, Auth Custom Token, Functions Node 20 TS, Storage | **Partiel** | Les initialisations et Functions existent, mais aucun projet Firebase réel n’est configuré ni déployé. Le runtime local est Node 22 ; Node 20 Firebase n’est pas validé en déploiement. |
| Stack desktop | Tauri 2, React 19, TypeScript, Vite, Tailwind 3.4, Lucide, PDF renderer | **Partiel** | Tauri/React/TS/Lucide sont présents et compilent. Le style est dans `apps/desktop/src/styles.css`, sans Tailwind 3.4. `@react-pdf/renderer` et la génération PDF bulletin ne sont pas présents. |
| Stack mobile | Expo 52, RN 0.76, Router 4, NativeWind 4, caméra, Lucide Native, notifications | **Partiel** | Le dépôt utilise Expo 54, RN 0.81.5, Router 6. `nativewind`, `lucide-react-native` et `expo-notifications` ne sont pas dans `apps/mobile/package.json`. Les écrans utilisent `StyleSheet`. |
| Monorepo | Turborepo 2, pnpm 9, `apps/desktop`, `apps/mobile`, `packages/shared`, UI partagée | **Partiel** | La structure et `pnpm-lock.yaml` existent. `packages/shared` reste concentré dans quelques fichiers et `packages/ui` contient surtout des tokens/types, pas les composants demandés. |
| Multi-écoles | `school_id` partout, isolation client + Rules | **Partiel** | Rules et helpers d’école existent, avec 4 tests Emulator. Plusieurs payloads d’interface restent locaux/codés en dur et le mobile de paiement utilise `school_id: 'mobile'`; les flux ne sont pas tous reliés à l’école issue des claims. |
| Schéma Firestore | Toutes les collections/sous-collections du cahier | **Partiel** | Les collections racines principales sont présentes dans les Rules, mais les sous-collections `eleves/{id}/notes`, `paiements`, `presences` prévues aux lignes 100–130 ne sont pas utilisées par le data layer actuel, qui écrit principalement `ecoles/{schoolId}/notes`, `paiements`, `presences`. |
| QR | Usage unique, 15 minutes, révocation, Custom Token | **Partiel avancé** | Création, consommation transactionnelle, expiration et Custom Token sont codés. Le test Emulator ne couvre pas encore l’ensemble du cycle QR, et l’écran mobile historique `app/qr.tsx` reste un flux duplicatif qui consomme sans ouvrir de session. |
| Appel | Créneau actif, classe/matière/prof automatiquement, batch, inverse rapide | **Partiel** | Le batch Function existe. L’écran mobile `(prof)/(tabs)/appel.tsx` affiche une classe, matière, date et horaire codés en dur et ne vérifie pas le planning actif. Le desktop utilise une classe fixe dans `AttendancePage`. |
| Notes | Classes/matières/trimestres affectés, appréciation, debounce 500 ms, statut sauvegarde | **Partiel** | Validation et callable `writeGrade` existent. L’écran mobile affiche uniquement Mathématiques/6ème primaire A/1er trimestre, sans sélecteurs, appréciation, debounce ni état par ligne. Le desktop conserve une liste de notes initiale. |
| Bulletins | Calcul, rang, mentions, blocage paiement, PDF Storage, impression forcée | **Partiel** | Un trigger recalcule une moyenne. Le rang, la mention, le blocage financier, les paramètres d’établissement et le PDF Storage ne sont pas intégrés dans un flux complet. Le bouton desktop d’impression forcée modifie seulement un état local. |
| Documents | Upload et rattachement école/élève/classe/année, permissions | **Partiel** | Une Function génère une URL Storage signée et les Rules Storage existent. Il n’y a pas de flux desktop/mobile d’upload, de métadonnées métier, de liste, de suppression ou de consultation document par document. |
| Élèves desktop | Formulaire complet, tri toutes colonnes, filtres sexe/section/statut, import intelligent, détail unifié | **Partiel** | Liste, recherche, filtres de base, ajout et détail visuel existent. Le tri complet, les filtres demandés, l’import par étapes avec correspondance/aperçu/doublons, les documents/timeline et les mutations cloud de transfert/désactivation sont incomplets ou locaux. |
| Historique scolaire | Identité permanente, inscriptions par année, promotion/redoublement/transfert/radiation | **Absent à partiel** | Le type `Student` contient une petite histoire locale, mais aucune collection d’inscriptions ni transaction de passage annuel n’est implémentée. |
| Structure école | Niveaux/filières configurables, modules masqués selon école, classes intelligentes | **Partiel** | Le desktop permet de cocher quelques libellés et d’ajouter un niveau localement. Les sections/options réelles, la persistance Firestore et le masquage fonctionnel des modules ne sont pas terminés. |
| Classes/sections/matières/trimestres | CRUD complet + affectation professeur | **Partiel** | Des pages desktop existent, mais les actions sont principalement `setState`/notifications. Il n’existe pas de couche Firestore complète pour ces entités ni les validations serveur par classe/matière/année. |
| Affectations enseignants | Plusieurs classes, matières, année, créneaux, titulaire, filtrage serveur | **Partiel** | Une collection `affectations` et un contrôle d’existence sont présents. La Function `writeGrade` ne vérifie pas encore la classe/matière de chaque note ; les listes mobiles ne proviennent pas des affectations. |
| Rôles personnalisés | Création de rôles et capacités en langage simple, enforcement backend | **Absent** | Les rôles fixes sont typés. L’écran Paramètres affiche un bouton « Créer un rôle personnalisé » qui notifie seulement ; aucune collection, Function ou Rule de capacités personnalisées n’existe. |
| Permissions fines | Rôle + affectation, secrétaire/surveillant/responsable pédagogique | **Partiel** | Les Rules gèrent plusieurs rôles et les tests couvrent un professeur non affecté. Les règles n’imposent pas encore toutes les affectations par classe/matière/année et le client conserve un sélecteur de rôle de démonstration. |
| Dashboard directeur | Données Firestore réelles, alertes actionnables, 5 derniers élèves/paiements | **Partiel** | Le dashboard visuel et plusieurs liens existent, mais les chiffres/activités de secours viennent de données initiales et les alertes ne sont pas entièrement calculées depuis les collections. |
| Dashboard professeur | Prochain cours, salle, tâches, notifications depuis planning | **Absent à partiel** | L’accueil mobile contient deux cartes statiques et une mention d’affectations ; aucun prochain cours issu du planning ni badge de messages non lus réel. |
| Absences enseignants/charge | Présence personnel, remplaçants proposés, heures/conflits/sous-affectation | **Absent** | Aucun modèle, Function ou écran complet identifié. |
| Messagerie | Conversations Firestore temps réel, destinataires collègues, messages non lus | **Partiel très faible** | Le desktop contient une page et des messages initiaux/localStorage. Il n’existe ni Function métier ni abonnement Firestore messages côté client/mobile ; aucune route mobile `messagerie.tsx`. |
| Notifications actionnables | Rappels appel, dossiers incomplets, absences, paiements, navigation | **Absent** | Aucun `expo-notifications`, token device, trigger de notification ou rappel planifié n’est implémenté. |
| Recherche universelle | Élèves, personnel, classes, matières, bulletins, factures, paiements, documents avec permissions | **Partiel** | La recherche desktop couvre élèves, personnel et classes depuis les tableaux locaux ; les autres domaines et la recherche serveur paginée manquent. |
| Comptabilité | Vue attendus/reçus/restant, historique, motifs/statuts, reçu imprimable | **Partiel** | Écran et callable paiement existent. La vue utilise des données initiales, le payload ne respecte pas encore tout le modèle métier, aucun reçu PDF/imprimable complet ni historique Firestore mobile n’est livré. |
| Licence/plans | Plan, dates, statut, limites, renouvellement, séparation finance école/licence | **Absent à partiel visuel** | L’écran affiche une carte « Plan School » et un bouton de renouvellement local. Aucun modèle, enforcement, catalogue configurable ou backend de licence n’existe. |
| Mobile Money | Préparation fournisseur, référence, rapprochement, remboursement, doublon, asynchrone | **Absent à partiel** | Le champ « Mobile Money » existe comme libellé. Il n’y a aucun modèle de facture/transaction complet, fournisseur, idempotence financière, webhook ou rapprochement réel. |
| Offline-first | IndexedDB, enable/disableNetwork, file de toutes les écritures, reprise, états | **Partiel** | Desktop active IndexedDB et écoute online/offline, mais n’a pas de file de reprise générique. Mobile possède une file AsyncStorage pour quelques callables, pas pour toutes les mutations et sans mécanisme réseau global. |
| Design system UI | Button/Card/Badge/Avatar/ProgressBar/Modal/Toast/Input/Select/Table/EmptyState | **Absent** | `packages/ui/src/index.ts` expose uniquement tokens, `ButtonVariant` et `UiButtonProps`; aucun composant partagé demandé n’est fourni. |
| Design/styling | Tailwind, glassmorphism, Inter, transitions 200 ms, scan animé | **Partiel** | L’identité visuelle et Inter sont visibles, la sidebar est conforme. Le desktop utilise CSS manuel et le scanner mobile n’a pas de contour animé ; NativeWind/Tailwind n’est pas branché. |
| États UI | loading, empty, error, success, messages français | **Partiel** | Plusieurs toasts et états existent. Les écrans mobile et certains modules desktop ont encore des données de démonstration et des états vides génériques ; la couverture d’erreurs métier n’est pas homogène. |
| Déploiement | Firebase réel, Hosting, EAS Android/iOS, Tauri Windows/macOS | **Non activé** | Aucun projet Firebase/secret n’a été fourni. Linux Tauri a été packagé ; les signatures et builds Android/iOS/Windows/macOS ne sont pas réalisés. |

## Écarts prioritaires à corriger

Les cinq écarts qui empêchent le plus directement de qualifier CLASSE de produit scolaire prêt à l’emploi sont la suppression des données initiales des parcours métier au profit de Firestore réel, le moteur d’inscriptions/transition annuelle, la gestion complète des affectations et permissions personnalisées, les flux PDF/documents/notifications, et le remplacement des écrans mobiles statiques par des données planning/élèves/paiements réellement filtrées par claims et affectations.

## Ce qui est effectivement validé

La migration physique du monorepo, le lockfile pnpm, le typecheck, le lint TypeScript, le build Vite/Functions, l’export web Expo, les tests Emulator d’isolation Firestore, la compilation Tauri et trois paquets Linux ont été exécutés. Le navigateur affiche bien CLASSE avec la sidebar rétractée et le logo visible, sans topbar permanente.

Ces validations prouvent la compilabilité et quelques fondations de sécurité ; elles ne prouvent pas la conformité fonctionnelle complète ni une connexion Firebase de production.
